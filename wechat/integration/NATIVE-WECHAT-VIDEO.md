# 微信视频文件的来源与读取（2026-10-23）

真实失败：群成员先要求查看另一名被真实 @ 成员的最新视频，再引用该视频提问。引用是 type49/type57，但 refermsg.type=43，正文只有 `null:2:0` 占位符。旧链路将此当成空引用并索要网页链接，实际上消息编号完整，原视频已经收到。

现在的链路：

1. `wechat_video_source.select_request` 优先选明确 type43 引用的服务器编号和原作者；没有引用时只接受一个真实 @ 的其他成员及“最新/刚发视频”等明确话语。私聊可定位主人的最近视频。不会从可见昵称或最近任意成员的图片猜测。
2. 使用绑定小号的已准备密钥与只读数据库，按会话、原作者、服务器编号查 type43。最新查询限请求时间之前，并按时间及 sort_seq 排序；冲突拒绝。不会访问主号或扫描进程。
3. 根据该行 packed_info 的唯一文件编号找小号缓存中的 MP4，检查路径、64 MB上限、MP4头和消息 XML 的 MD5。缺完整文件时返回“已定位但未下载”，而不是“没收到/空引用/缺链接”。
4. 在聊天生成之前调用媒体服务 `/incoming-video`：最多六帧分布采样、最多前120秒音轨、35秒总预算。外部视频内容标为资料，不提供工具权限。不给模型原始缓存路径、AES密钥、CDN附件标识。
5. 将当前视频范围一并交给酒馆/DSH候选检查；普通点评中不主动汇报抽帧过程，用户追问范围时准确解释。检查最多一次无工具改写，不重新执行动作。

实际验证：原群引用编号 `11000054`，211535字节，原作者和 XML MD5一致。最初只有缩略图。使用 computer-use 在绑定小号窗口点击这条明确引用，原生客户端取回 MP4，之后关闭查看器；主号未操作。实际媒体API读到约1.85秒视频的六帧，没有可靠音轨转写。

通过原引用和“查看被@成员最新视频”两种真实请求，在独立 Tavern evaluation 对话回放均解析到同一正确视频并能评论实际画面，正式聊天记录未被评测改动；没有补发旧请求或向微信群发送测试消息。来源、跨会话隔离、冲突、哈希、防止索要链接及候选检查已做回归测试。
